**Mutation-check / test discipline**
- A sibling signal can mask the guard under test — when a mutation survives, suspect the test's setup before the code. Add a fixture row that matches every filter except the one under test (decoys carry the opposite value of every field a write sets; fixture ids must differ across joined columns, e.g. actid ≠ actwho, or a wrong-join mutant survives).
- Mutation recipe: `cp` backup into a fresh `mktemp -d` per run (a reused/fixed /tmp dir once skipped a restore) → edit with `sed`/`perl -0pi` (or a Python driver: exact-once replace) while the dev server hot-reloads → run the test file(s) → restore → `cmp`/`shasum` byte-compare. Never `git checkout --` uncommitted work (it once destroyed an in-progress fix). A mutation that inserts a non-ASCII char can double-encode an existing multi-byte one (e.g. "⏱") and redden unrelated tests — use ASCII.
- One named test per guard/mutation letter makes the readout unambiguous (each mutation should redden exactly one named assertion). Keep one guard per property (no redundant second filter that masks the first); split read-count vs write-count negatives. Mutate shared `run*` bodies, not thin `actions.ts`, since unit tests inject deps; to isolate one action's admin check inside a shared body, mutate with `&& where !== "<op>"`.
- Fake PostgREST/SQL clients must actually apply the filters given (eq/neq/gt/gte/lt/lte/is/in/not/order/limit/single, project the select list) and throw on anything unsupported — a fake that ignores unknown filters misses loader-side mutations. Known limits: `create-sql.test.mjs`'s fake supports only select/order/limit/insert (phrase `.eq` mutants another way); `tests/money/fakedb.mjs` `order()` is a no-op and it lacks `not in` (so `listAccounts` is live-only); `tests/docs-reports/fakedb.mjs` supports `not(col,"like",v)` and `or(expr)` but treats NULL as passing for `not … like` (safe only because `workStatus()` chains `.not("casestatpriority","is",null)` first — add a chained null guard in any fixture that reuses it). A fake for an upsert must enforce the unique key and fail a colliding plain insert as a whole statement. Race/undo paths (create-bill, revise, reversal, pay-link, finalize, review-inbox) can only be seen through a fake that flips state between the pre-check read and the guarded write (an awaited hook to interleave both inserts); the `actbillid is null` filter is isolable only in a fake because a check constraint forbids that pair.
- Tests that loop over the module's own constant let a dropped entry survive — pin lists as literals. Live tests must drive the app's real queries, not hand-written SQL. Proving read-only by a write counter on the fake beats grepping for `insert|update|delete`. For a "must not re-query" guardrail, trace every fake-Db call and `deepEqual` it against the reference path.
- A live "nothing was inserted" negative must scope its count/cleanup to include the exact row a bug would produce (e.g. `actwho.eq.1,actwho.is.null`, not just `actwho = PERSON`) or it goes vacuous and the bad row leaks. Remember that unit-green does not cover error-path guardrails (a green QA missed an error-path breach that only review caught) and that a mapping discriminating on one field must be checked for two distinct failures sharing that value (see Storage below).
- Live fixtures leave rows behind unless there is a delete path; use a dedicated id range per lane and delete by exact values (grep before assuming a range is free): contacts lane leaves `"Contacts Live <tag>"` rows with no delete; billing live ranges 9908xx (`notice.live` deletes all of 990800–990899 at cleanup), 991000–991099 (recipient alert), 9913xx (bills panel/case wiring), 9914xx (time-bill-links, in use as of 991401); money uses case 990901 (the live test creates and deletes it — it does not exist on hosted) and decoy case 990902; cases/inquiries reuse fixed ids (actid 12, case 90005, inquiry 33). Journey 02 creates a tblcase + tblinquiry and journey 03 a tblactivity row on hosted each run. Test helpers that add lookup values to the hosted DB must remove leftovers at setup and re-point FK rows before deleting (an invented "Low" priority leaked once); `ensureOpenStatus` in `tests/cases/seed-fixtures.ts` adds an invented "Open" row. Cleanup order: `tblfundsrcvd.fndsbillid` is a FK to `tblbills`, so delete funds before bills. Hosted case 90001 may carry stray unbilled hours from earlier runs — don't assert absolute totals on it.

Prove a server action's admin check by capturing the admin's real request (`next-action` header + body) and replaying it with a staff cookie; run the admin replay first as a control. **Auth / app-shell conventions**
- `safe-next.ts`'s pattern is `/^\/(?![\/\\])/` plus a control-character reject; Next itself normalizes `//x` to `/x` before middleware, so the `next=` guard is defense-in-depth — any page using `next=` must still validate it.
- `config.matcher` exclusions must be escaped, `$`-terminated literal prefixes, never an extension pattern (an extension matcher once let an auth boundary skip `/cases/<id>.js`); any future `public/`-style dir needs a literal prefix.
- Middleware makes 2 Supabase calls per request (a JWT role claim, out of lane, would halve that). The root layout calls `getSession()` twice per render (layout + page; React `cache()` would cut it to one) and has no timeout on it, unlike middleware's 2s. The case page calls `requireSession()` twice per render (one extra profiles read) because the page discards its result and a panel re-derives it.
- `@supabase/ssr` 0.12 caches Set-Cookie values in memory (`setItems`), so a server action can query as the user right after `signInWithPassword` on the same client.
- Server-action encoding: Next 14.2 server actions only read form fields that come before the trailing numeric "action id" part of the payload — fields appended at the end of a crafted/replayed POST are silently ignored; inject extras BEFORE the real fields and assert they were inserted. On Next 14.2.18 a `Next-Action` header under curl 500s ("Connection closed."); only the progressive-enhancement form POST works. The `sb-127-` cookie prefix is a cheap proof the app bound to the LOCAL stack.
- Admin/role guards must compare against the id loaded from the database (Postgres uuid comparison is case-insensitive; a raw-string compare was bypassable with an uppercase uuid). A delete/update that re-checks a role must put the role in the `.eq()` of the write itself. Last-admin protection (no migration): pre-check ≥2 admins, role-conditional write, recount and undo if zero (failed undo detected by rows-affected); with a single admin "last admin refused" is exercisable only via self-deactivation — test through a fake client.
- Rate limiting: a 429 on re-auth (password change) has its own "Too many attempts" message; `app/(auth)/login/actions.ts` still maps every sign-in error including 429 to `error=invalid` (known follow-up, not fixed). Live sign-in tests retry with backoff on 429 and never count it as accepted or rejected — parallel items on one Supabase project hit this routinely.
- Changing a password does not sign out other sessions (deferred). Deactivation deletes only the `profiles` row (auth user kept); reactivation is detected via the primary-key conflict on insert (Postgres `23505`), which also means "already exists" for duplicate-email creation. A signed-in user opening `/login` is not redirected away (never asked for).
- Staff hitting an admin-only page must get a clean "Admins only." (200, not 500): there is NO `app/error.tsx`, so every page/server action must catch `ForbiddenError` itself (`requireSession("admin").catch(onlyForbidden)`).
