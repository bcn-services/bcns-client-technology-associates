### Mutation-check and test discipline
- When a mutation survives, suspect the test's setup before the code — a sibling signal can mask the guard (an unrelated mismatch fails the run first).
- Convention: one named test per guard ("guard <letter>"), each reddening exactly one assertion. Isolate mutants (a first-letter mutation that also reddens another guard, e.g. 'Paid' matching 'Partial Payment', must be rebuilt as an exact case-insensitive match). Mutate where the code is called from (the unit tests inject deps, so editing `actions.ts` would go unseen — mutate the check inside `run*`); mutate one table at a time when one loop serves two; mutate at the prop source (`page.tsx`), not in an effect branch a redirect never re-triggers.
- Mutation mechanics: edit with `sed`/`perl -0pi` (hot-reload keeps a warm server usable) → run → restore from a `cp` backup in a fresh `mktemp -d` per run (a reused fixed /tmp dir lost backups twice) → byte-compare (`cmp`/`shasum`). Never `git checkout --` uncommitted work. A non-ASCII replacement double-encodes existing multi-byte chars (e.g. "⏱") and reddens unrelated tests — use ASCII. A 4-run live mutation loop takes >10 min: run it in the background from the start.
- Fake PostgREST/SQL clients must really apply every filter they are given (eq/neq/gt/gte/lt/lte/is/in/not/or/order/limit/single), project the select list, enforce unique keys on upsert (a colliding plain insert must fail as a whole statement) and throw on anything unsupported — otherwise loader-side mutants survive. Known gaps: `tests/money/fakedb.mjs` `order()` is a no-op and `not` supports only `is` (no `not in`, so `listAccounts` is live-only); `tests/docs-reports/fakedb.mjs` supports `not(col,"like",v)` and `or()` but its `not like` treats NULL as passing (SQL does not) — chain a null guard in any fixture reusing it; the fake in `tests/cases/create-sql.test.mjs` supports only select/order/limit/insert (phrase `.eq` mutations differently; dropping `caseid` fails with `column "nan"`, so the unit payload test is the real guard).
- Fixtures: ids must differ across joined columns (actid ≠ actwho); add a decoy matching every filter except the one under test; decoys carry the opposite value of every field a write sets; a "nothing inserted" live count must include the row the bug would write (`actwho IS NULL`) or it goes vacuous and the row leaks past cleanup. Tests that loop over the module's own constant let a dropped entry survive — pin lists as literals. Live tests must drive the app's real queries, not hand-written SQL. A mutant for a distinct failure mode sharing one field value (e.g. two different 404s) cannot be found by a mutation battery — check what other failures carry the same value.
- A guard "must not re-query / must equal the screen" is proven by tracing every fake-Db call and `deepEqual`-ing the traces. Proving read-only: a write counter on the fake beats grepping for `insert|update|delete`. Round-trip generated files (xlsx via `writeBuffer()` + reload) to catch lost formats; a refactor of a renderer is proven safe by a byte-identity test against the prior commit across several setups.
- Server-action tests: capture the admin's real request (`next-action` header + body) and replay it with a staff cookie; run an admin replay first as a control. Next only reads form fields BEFORE the trailing numeric action-id part — extra fields in a crafted POST must be inserted before the real ones (assert they were inserted). Live replay tests that depend on an earlier test's captured request must run as a whole file, never with `--test-name-pattern`. On Next 14.2.x a `Next-Action` header POST 500s ("Connection closed.") under curl — only the progressive-enhancement form POST works there. Middleware makes a route's own `requireSession` unobservable over HTTP — cover it with a static/unit check; `requireSession()` also can't run under tsx, so a `personId`-null/session guard is proven only by a live replay with an unlinked login (or a source-reading test). Test the real `config.matcher` regex in a dependency-free node test.
- Every test `formFor` for an edit form must send `__orig` or it proves nothing; seed rows with browser-altered values (CRLF, leading/trailing spaces, leading textarea newline, off-list value) and check an untouched save leaves them identical.
- Playwright: button names match by substring (avoid new "Save …" labels near another form's `name: "Save"`); a `<label>` wrapping a `<select>` pulls option text into the accessible name so `getByLabel` times out (use `htmlFor` + `id`); Next's route announcer has `role="alert"` (find the login error by text); `/i` substring assertions go strict-mode-fragile the moment a page renders two labels where one contains the other (check the whole label set against every journey regex before building — `getByText(/firm/i)`, `/due/i` vs "Overdue", `/billed/i` vs "Unbilled hours"; use headings, `^…$` or test ids). Seeding `localStorage` with a past `startedAt` proves timer flows without waiting; capturing the server-action RSC response via route interception locates payload bugs fast.
- Grep every caller before changing a shared seed/test helper (a changed `seedE2eUser` default once linked every throwaway/admin account to a real `personid`). Live fixtures with no delete path leave rows: keep a dedicated id range per lane and delete by exact values. Hosted live ranges in use: contacts "Contacts Live <tag>" rows; billing 9908xx (notice.live deletes ALL of 990800–990899), 9910xx (recipient alert), 9913xx (case wiring), 9914xx (time-bill-links, 991401); money case 990901 (live test creates/deletes it) and decoy 990902; billing-output 9937xx (QA i7); journeys 02/03 create a case + inquiry + tblactivity row each run with reused ids (actid 12, case 90005, inquiry 33 — delete by exact values). Test helpers that add lookup values to the hosted DB must remove leftovers at setup and re-point FK rows before deleting (an invented "Low" priority leaked once). Hosted case 90001 carried stray unbilled hours from earlier runs (3.500 when checked) — don't assert absolute totals on it. Never mutation-check a filter live if it would rewrite real hosted fixture data (the "billed" filter on hosted `tblactivity` row 2: `actbilled=true, actbillid=null`).
- Rate limits: two items on one Supabase project hit auth 429s — live sign-in checks must retry with backoff and never count a 429 as accepted or rejected. Live admin-count tests skip themselves when a concurrent run holds admin. The live login test failed 3 of 6 when the gate suite ran concurrently — run it alone.
- Storage live tests need `try/finally` with `storage.remove([key])`; `tests/docs-reports/storage-adapter.test.mjs` still leaks one object per run (it puts `key` and never removes it; only the 105-object paging test cleans up). Local-stack tests are gated by `DOCS_REPORTS_LOCAL_STACK` + `.env.test.local` (`tests/docs-reports/local-stack-setup.sh`); the `sb-127-` cookie prefix proves the app bound to the LOCAL stack, not hosted.

### Schema and hosted-DB conventions
- Hosted `tblcasestatus` has only "Active", not "Open": new-case default is "Open" only when the status list has it (`lib/cases/create.ts`); convert-inquiry refuses when "Open" is missing, and `ensureOpenStatus` (`tests/cases/seed-fixtures.ts`) adds an invented row on hosted — check the real status list before a feature relies on "Open". `tblcase.tabranch` is `NOT NULL` (any case-creating flow needs a branch default/picker). Hosted case numbers are 90002+ (>32767), so `inqresultingcase` is never written — "already converted" must look up `tblcase.caseinquiry`.
- `case_search` (migrations `0007`, widened by `0011`) has no `caseid::text`, so case # search is exact-match only (`lib/cases/search.ts`); if a hosted DB hasn't had them pushed, `/cases?q=` and the case lists show a missing-view alert (PGRST205/42P01; search-error detection also matches `/case_search/` loosely). PostgREST turns a typed `*` into an unescapable LIKE wildcard; `escapeLike` handles `%`/`_`; OR values in `.or()` must be double-quoted with `\` and `"` escaped; PostgREST can't `ilike` id/inqdate (inquiry search substring-matches in JS over an `id, inqdate` scan and ORs `id.in.(...)`) or order by `lower(text)`/"is null" (presets sort in JS). Case lists read `tblcase` without joins and fill names from the view by id so orphan cases stay visible. Deferred Minors: repeated `?q=` → array → 500; raw DB errors shown to the user; serial status-list + search reads; AND search mixing view/`tblcase` fields intersects 1000-row pages in memory.
- Reads join in JS and are capped at 1000 rows per page (marked `ponytail:`): presets, service-auth lists ("Recently approved" has no limit), `listCaseTime`, `listCaseFunds`, contacts presets (move to a view if `tblcase` outgrows ~50k rows). `lib/audit/list.ts` is keyset-paged because the audit table is ~550k rows. `/expenses` dev-mode headroom is only ~100–200 ms under the 1 s bound at 5,000 rows (re-time any per-row markup; fetch pages in parallel past max-rows); `?case=` alone means the whole ledger with no month default. The `/bills` list perf live test churns ~10k hosted audit rows per run.
- `tblexptype.active` is typed `boolean|null` though the migration says not null default false — keep `.eq("active", true)`; later money forms' type selects import `listActiveTypes` (`lib/expenses/types.ts`). Hosted `fndsclearedbank` defaults false, not null — "uncleared" is `.not(flag, "is", true)`. `expinit` is a smallint FK to `tblbillingnames.personid` (a select, not free text). `tblfundsrcvd.fndsbillid` is a FK to `tblbills` — cleanups delete funds before bills. Money parsers: `lib/expenses/save.ts` `parseMoney(raw, code)` and `lib/funds/money.ts` `parseMoney(raw)` both exist (`lib/bills` `fmtMoney` is float display only) — reuse or consolidate rather than add a third. Money is integer cents / decimal strings end to end (float-sum mutants go red only on large-amount fixtures).
- `billingfactor` is numeric(8,3) and `tblbilllines.rate` numeric(10,2): round the scaled rate half-up to integer cents BEFORE multiplying or storing (`lib/bills/rates.ts`).
- Write-and-guard patterns: put ownership/state filters on the WRITE statement itself and use `.select()` to detect zero rows (`editableOnly()` in `lib/time/entries.ts`, `guardedUpdate` in `lib/bills/notice.ts`: `.eq(billnotice, expected)` + `.is(date_col, null)` + count ≠ 1 → stale). A write that returns an error may still have committed — compensate only on a clean 0-row result and test the "fake applies the write then errors" case. Insert inert, promote after the guard wins, so a failed compensation leaves harmless data; make the primary key the once-only guard where possible (reversal inserted with `fndsid = -original`; 23505 = already done); link-first ordering (the write that must win the guard goes ahead of its effect). Finalize: claim (`update … where billfinalizedat is null`) → bulk insert lines → on failure release the stamp guarded on still-ours; `canFinalizeBill` in `lib/bills/rules.ts` is the one rule for button, page and save (likewise `canSendBill`/`canSendNotice`). Last-admin protection without a migration: pre-check ≥2 admins, role-conditional write, recount and undo if zero (failed undo detected by rows affected); with one admin it is exercisable only as self-deactivation via a fake client. Upsert imports: one upsert with `ignoreDuplicates` on the frozen key (imported = returned rows) is atomic and concurrent-safe; parse the whole file before any DB call. Reactivation of a returning auth user with no `profiles` row: detect via the insert's 23505, not a separate select (23505 also means "already exists" for duplicate-email creation).
- Compare ids against values loaded from the database, not raw form strings (Postgres uuid matching is case-insensitive — an uppercase uuid bypassed a self guard); a delete/update re-checking a role must include it in the write's `.eq("role", row.role)`.
